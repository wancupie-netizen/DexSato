# 03-E.2E.4 — Live Read-Only Account Snapshot & Identity Verification

## Scope

Operator-only evidence collector. It validates the unsigned transaction/order
locally before making any request, verifies the RPC reports Solana mainnet, then
uses only `getMultipleAccounts` with `finalized`. It never signs, simulates,
submits, creates or modifies accounts, claims fees, calls Jupiter, or changes
application runtime. Production files, formulas, UI and fee gate are untouched.

Baseline: uploaded E2E1 ZIP plus exact E2E1–E2E3 installer outputs, reported
committed through f4e4ab1. Installer hashes normalized contents and stops before
all writes on drift. Four targets: the new collector, tests, this note and one
pytest.ini registration. Existing requests/solders dependencies are reused.

## Prepare intent independently

Use one recent `unsigned_evidence.json` generated by the existing E1A capture.
Do not put a seed phrase, private key, wallet export, API key or RPC URL in the
intent file. All fields are public addresses/hashes.

Create `live_identity_intent.json`:

```json
{
  "wallet": "PUBLIC_WALLET_ADDRESS_YOU_APPROVED",
  "input_mint": "PUBLIC_INPUT_MINT_YOU_APPROVED",
  "output_mint": "PUBLIC_OUTPUT_MINT_YOU_APPROVED",
  "source_token_account": "EXPECTED_EXISTING_SOURCE_TOKEN_ACCOUNT",
  "destination_token_account": "EXPECTED_EXISTING_DESTINATION_TOKEN_ACCOUNT",
  "message_sha256": "64_LOWERCASE_HEX_MESSAGE_HASH"
}
```

Do not blindly copy all five identities from an untrusted order. Wallet and mints
must reflect operator intent. Source/destination candidates may be inspected in
the resolved V2 instruction roles 2 and 5, but verify them independently using
the wallet/explorer or known account derivation before recording intent. The
message hash must refer to the versioned message, not whole transaction; use the
hash produced by the existing decoder/byte-binding evidence.

The captured order must include `transaction`, `taker`, `inputMint`, `outputMint`,
`inAmount`, `outAmount`, `otherAmountThreshold` and integer `slippageBps`.

## Run live read-only verification

Set `SOLANA_RPC_URL` to a configured HTTPS mainnet RPC in the current PowerShell
session. Never paste that URL into reports or chat if it contains a provider key.

```powershell
python -m application.jupiter_live_identity_snapshot `
  --evidence ".\PATH\unsigned_evidence.json" `
  --intent ".\live_identity_intent.json" `
  --output-dir ".\phase03e2e4_live_001"
```

Exit code 2 means review-required evidence was written; it is intentional, not
execution approval. Expected console shape:

```json
{"status":"LIVE_IDENTITY_REVIEW_REQUIRED","execution_ready":false,"fee_receipt_verified":false}
```

Upload `phase03e2e4_live_001/live_identity_report.json` for review. The companion
`live_account_snapshot.json` contains public on-chain raw account bytes and no
configured endpoint, headers or credentials. Upload it only if requested for
byte-level diagnosis. Inspect files before sharing as normal operational hygiene.

If the result is `ACCOUNT_NOT_FOUND_AT_SNAPSHOT`, do not create anything and do
not switch off validation. The account may be intended for creation inside the
transaction; E2E4 deliberately does not infer that. Capture a fresh order or
request separate support review. A failed run reserves its output directory;
choose a new directory for retry.

## Evidence model and limitations

The collector first performs E2E2 byte/hash/minimum-header checks and basic
order intent checks, before any RPC request. It extracts ALT addresses from the
actual transaction and fetches those plus the independently expected two token
accounts and two mints in one `getMultipleAccounts` call. Only owner, executable
and canonical base64 raw data are retained. E2E3 then verifies ALT ordering,
wallet/payer/authority, mint and token account identities.

The report records request/check timestamps, finalized slot, requested addresses,
missing addresses and data hashes via the nested binding. These are provider
observations, not cryptographic account proofs. TLS plus a mainnet genesis result
does not authenticate the snapshot. A configured malicious/compromised RPC can
forge both responses. The snapshot is current-state, not necessarily the bank at
which Jupiter built the order. Recent blockhash validity and transaction expiry
are not checked here.

Accordingly, even a consistent result keeps:

- `status: LIVE_IDENTITY_REVIEW_REQUIRED`
- `snapshot_authenticity_verified: false`
- `transaction_recency_verified: false`
- `execution_ready: false`
- `fee_receipt_verified: false`
- inherited broad transaction/enforcement flags false

It does not verify full route/CPI effects, programs/deployments, minimum semantics,
fees or eventual receipt. Classic existing SPL Token accounts only; Token-2022,
pre-create ATA, delegates and close authorities remain unsupported by this
harness. This is not wired into the production order endpoint.

## Verification performed before delivery

17 new tests cover successful read-only orchestration, missing accounts, intent
mismatch before RPC, HTTPS validation, wrong network, duplicate/invalid JSON,
response bounds/closing, malformed slots/counts/owners/encodings. Together with
E2E1–E2E3, 121 tests passed locally. Tests use deterministic fake RPC responses;
no claim of a live mainnet verification is made until the operator report exists.

## Commit only after full regression and report review

Do not commit merely because the installer completed. First run full regression,
then produce/review the live report. If code tests pass but live identity fails,
the harness may still be committed as audit tooling, but fee execution remains
blocked and the failure must be documented.

```powershell

```
